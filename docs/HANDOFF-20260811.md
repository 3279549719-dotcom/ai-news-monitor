## 三、下一步任务：管线搬 GitHub（crawl4ai 方案）

### 3.1 Patrick 的决策

- ✅ 搬到 GitHub Actions
- ✅ **用 crawl4ai 方案**（每次 Actions 动态启动 Docker 容器）
- ❌ 不用 Firecrawl API 替代
- ✅ 用三 Agent 架构完成改造

### 3.2 技术分析

**可行，但有几个关键点**：

1. **GitHub Actions 支持 Docker**：`ubuntu-latest` runner 自带 Docker，可以直接 `docker run` crawl4ai
2. **crawl4ai 镜像**：需要公开可用的 crawl4ai Docker 镜像（或从 Docker Hub 拉取）
3. **DeepSeek / Supabase 凭据**：需要作为 GitHub Secrets 配置
4. **X 平台抓取**：`scripts/x-fetch-tweets.py` 依赖 twikit，Python 环境需要预先安装
5. **管线入口**：`node scripts/run-pipeline.js` 或 `node src/index.js` → 需要确保 crawl4ai 健康后再跑
6. **报告生成/邮件推送**：管线内部的 `src/email.js` + `src/notify.js` 仍可正常工作

### 3.3 大致改造清单

| 改造项 | 说明 |
|--------|------|
| 新建 `.github/workflows/daily-pipeline.yml` | cron `0 0 * * *`（北京时间 08:00） |
| 确保 crawl4ai Docker 在 workflow 中启动 | `docker run -d -p 11235:11235 --name crawl4ai <镜像>` |
| 配置 GitHub Secrets | `DEEPSEEK_API_KEY`、`SUPABASE_URL`、`SUPABASE_SERVICE_KEY`、`EMAIL_*` 等 |
| 处理 X 平台 twikit | 可能需要首次交互登录，不好自动化。如果是 GitHub Actions→建议跳过 X 抓取，或保留 X 手动跑 |
| 管线验证 | workflow 末尾跑 `npm run check` |
| 管线失败通知 | 复用 `src/notify.js` 或 Actions 自带的 `if: failure()` |
| 降级链保持 | crawl4ai 不可用→降级 `scraper-direct.js`（已有逻辑，保底） |

**最大的风险是 X/twikit**：它需要浏览器交互登录，在 CI 环境可能无法自动化。建议先跳过 X 抓取（标记为后续手动处理），保证 T0 信源 + 白名单信源能通过 crawl4ai 正常跑。
