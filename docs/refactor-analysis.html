🔍 识别到的 8 个结构性问题

#问题影响严重度所在位置
1 index.js 超重 — 主入口 ~410 行，混入 pipeline 调度、过滤函数、评分逻辑、入库构造等 5 类职责 改一处要全读，新成员无从下手；任何 pipeline 修改都在同一个 410 行文件里博弈 高 src/index.js
2 配置分散 — T0_FLOOR、T1_FLOOR、RESULT_LIMIT 在 index.js 硬编码，config.js 也有自己的 MIN_SCORE 定义 调评分/放行线要同时改两个文件，容易遗漏；配置源不唯一 中 config.js + index.js
3 PIPELINES 对象是纯配置 — 放在 index.js 里和调度逻辑混在一起，类型定义 + 函数引用混合 新增 pipeline 类型要改 index.js 主入口；无法独立测试 pipeline 路由 中 index.js L82-L92
4 keyword-roots 硬编码词根 — 关键词->词根的映射写在代码里而非数据文件 新增关键词需改 JS 源码，不符合"新增信源改数据不改代码"的设计原则 中 src/keyword-roots.js
5 模块依赖环 — notify.js ↔ email.js 互相 require（通过惰性 require 缓解但未根治） 环形依赖在极端场景下可能导致部分初始化失败；理解成本高 中 notify.js + email.js
6 遗留代码未隔离 — scraper.js、reader.js 两个 LEGACY 模块仍与活跃代码同目录 新人误读、误改遗留代码；CI 不会提示"你改了 LEGACY" 低 src/scraper.js, src/reader.js
7 配置含敏感信息 — config.js 顶层直接 require('dotenv').config() 并暴露全部 env；DEEPSEEK_API_KEY 等直接挂在 exports 上 任何 require('./config') 都能拿到所有密钥；测试 mock 需整体替换 config 对象 中 src/config.js
8 fetch-chain 通道注册硬编码 — BACKENDS 对象在 fetch-chain.js 里定义，通道函数引用写死 新增通道（如 RSS、GraphQL）必须改 fetch-chain 源码 低 src/fetch-chain.js

🎯 三种重构方案对比

方案 A：轻量整理 低风险
工时 ~1.5h · 改动文件 5-7 个 · 不改变模块边界

只做低风险的集中化：把散落的配置常量统一到 config.js，把 index.js 中的纯函数（preFilter / applyTierFloor / toArticleRecord）按职责分发到已有模块（keyword-roots.js / tiers.js / items.js），遗留模块移入 legacy/。

具体改动

文件改动风险
config.js新增 T0_FLOOR / T1_FLOOR / RESULT_LIMIT / PIPELINES 常量；补全缺失的集中读取低
keyword-roots.js改为从 keyword-roots.json 数据文件加载（不改数据内容）低
index.js移除硬编码常量，改为 require config；preFilter 移到 keyword-roots，applyTierFloor 移到 tiers；toArticleRecord 移到 items中
scraper.js / reader.js移入 src/legacy/ 目录，更新 index.js 引用路径低
notify.js / email.js打破循环依赖：email.js 不再 require notify.js，改为上游 index.js 调 notify 分发中
方案 B：分层重构 推荐
工时 ~3-4h · 改动文件 12-15 个 · 新增 3-4 个模块 · 分层 directory

按职责把 flat src/ 重组为四层：config/（配置分离）、fetch/（抓取通道）、pipeline/（调度 + 评分 + 过滤）、output/（报告 + 邮件 + 通知）。index.js 瘦身到 ~100 行纯编排。保留所有 CommonJS 兼容和现有 API。

收益

  • index.js 从 410 行 → ~100 行，只做编排不包含业务逻辑
  • 每个目录有明确的单一职责，新增成员按功能定位文件
  • 配置与代码彻底分离，调放行线改 constants.js 即可
  • fetch 通道可以独立测试，pipeline stages 可以独立测试
  • 打破 notify/email 环依赖
  • 向后兼容：所有 require 路径变更集中在模块边界，测试只需更新 require 路径

风险

  • 文件移动 + 重命名，所有测试的 require 路径需同步更新（7 个测试文件）
  • fetch-chain.js 中的通道注册函数引用路径需更新
  • scripts/ 下脚本可能直接 require src/ 模块，需逐一检查
方案 C：激进重写 高风险
工时 1-2 天 · 改动 90%+ 文件 · 建议推迟

引入 TypeScript、IoC 容器、ES Module、插件化通道注册。channel registry 从硬编码变为文件系统扫描 / 配置驱动。pipelines 从函数变为 Pipeline 类。

  • 风险极高：当前管线每天运行，全量重写可能引入回归 bug
  • TypeScript 迁移需同时改前端构建链（client 已是 TS）
  • 收益不明确：当前 18 模块的复杂度完全不需要 IoC
  • 建议等到管线模块数 > 30 或多人协作频率 > 3 时再做

📋 决策建议

🏆 推荐方案 B：分层重构

理由：风险可控（不改业务逻辑，只重组文件），收益明确（index.js 瘦身、职责分离、新人友好），所有改动都可被现有测试覆盖验证。

最关键的改动只有两类：① 文件重命名/移动 + require 路径更新 ② index.js 拆分 + 全局常量统一到 config。两类的回归风险都被测试覆盖。

❌ 如果不重构

  • index.js 继续膨胀，每次加功能都在 410 行里塞
  • 新成员/LLM 需要全读 410 行才能定位修改点
  • 配置分散导致调参遗漏
  • 遗留代码污染活跃目录

✅ 重构后

  • index.js ~100 行，5 秒理解主流程
  • 按目录功能找文件：fetch/（抓取）、pipeline/（编排）、ai/（AI）
  • 调评分行 → src/config/constants.js 一处改
  • legacy/ 目录一目了然
