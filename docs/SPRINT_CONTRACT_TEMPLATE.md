## 二、Evaluator 审核清单

> Generator 在提交 Sprint Contract 时预填此清单，Evaluator 逐项审核后勾选。

### 2.1 理解检查（Generator 是否正确理解了需求？）

| # | 检查项 | 通过标准 | Evaluator 判定 |
|---|--------|---------|---------------|
| C1 | 目标对齐 | Generator 声明的"我要构建什么"与 REQ 目标一致，无遗漏、无曲解 | ☐ 通过 ☐ 不通过 |
| C2 | 范围边界 | "本次不做"列表完整，不含隐式扩大范围（如顺手重构无关模块） | ☐ 通过 ☐ 不通过 |
| C3 | 数据影响 | 是否涉及新增/修改持久化数据、表结构、配置项？如是，方案已在 REQ/DECISION 中确认 | ☐ 通过 ☐ 不通过 ☐ 不涉及 |

### 2.2 验证检查（验证方案是否可执行、可判定？）

| # | 检查项 | 通过标准 | Evaluator 判定 |
|---|--------|---------|---------------|
| V1 | 正常路径可验 | 每个验证步骤都是具体的、可执行的命令或操作，不是"检查功能正常"这种笼统描述 | ☐ 通过 ☐ 不通过 |
| V2 | 边界覆盖 | 验证覆盖了至少 1 个异常/边界情况（如：空数据、网络不可达、已存在数据冲突） | ☐ 通过 ☐ 不通过 |
| V3 | 回归闸门 | 验证方案包含 `npm run check` 全绿作为回归门禁 | ☐ 通过 ☐ 不通过 |
| V4 | 证据可查 | 每个验证步骤指定了证据形式，不以"应该没问题"代替 | ☐ 通过 ☐ 不通过 |

### 2.3 安全与护栏检查（改动是否会触发已知陷阱？）

| # | 检查项 | 通过标准 | Evaluator 判定 |
|---|--------|---------|---------------|
| S1 | 已知陷阱规避 | 改动不触发 `docs/KNOWN_TRAPS.md` 中的已知陷阱 | ☐ 通过 ☐ 不通过 |
| S2 | 硬反向操作 | 如涉及删数据/改历史/外部 API 写，已有 `--dry-run` 机制或人工确认门禁 | ☐ 通过 ☐ 不通过 ☐ 不涉及 |
| S3 | 密钥安全 | 不改动 `.env*` 结构、不新增密钥依赖、不提交密钥（如涉及，已在 REQ 中确认） | ☐ 通过 ☐ 不通过 ☐ 不涉及 |
