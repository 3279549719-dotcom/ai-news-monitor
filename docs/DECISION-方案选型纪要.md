# DECISION: 曼联信源监控技术方案选型纪要

> 决策日期: 2026-08-03 ｜ 参与: Patrick + Alice + 豆包
> 最后更新: 2026-08-03（加入方案化简优化章节）

---

## 决策背景

Patrick 设计了完整的曼联海外信源监控体系（含 5 级 Tier、交叉校验、四板块报告等），需要落地为可运行的实际系统。Alice 调研了项目现有代码（spec-001/002）和基础设施（Firecrawl API Key 已就绪），提出三个递进方案。经三方对齐后达成一致。

---

## 最终决策：白名单前置准入 + 必要校验保留

### 核心思路

**"源头锁死 T0/T1/T2，彻底放弃全网搜索。"**

旧方案：Google News 全网搜索 → 抓取 → 全量入库 → 后置过滤 T3/T4 垃圾源。

新方案：Supabase `keyword_sources` 表只配 T0-T2 高可信信源 → Firecrawl 只请求白名单 URL → T3/T4 从根源不存在。

### 选择理由

1. **结果等价、成本更低**：前后两种方案最终留存的都是同一批 T0-T2 内容，但白名单方案不浪费任何 API 调用在垃圾源上。
2. **运维简单**：新增信源只需在 Supabase 加一行记录，不改代码；不需要维护黑名单正则。
3. **Firecrawl + Supabase + DeepSeek 完全覆盖**：不需要引入额外的 X API、RSS parser、Google News 聚合等组件。
4. **渐进可升级**：当前先跑通定向抓取+独立评分（≈spec-002 已有代码），交叉校验和分类报告作为后续迭代。

## 方案化简优化说明

### 明确可砍掉的冗余模块

| 移除项 | 原因 | 节省 |
|--------|------|------|
| Google News RSS 全网搜索 | 白名单定向抓取替代 | 代码 ~100 行 + 每次运行 10-20 次 HTTP 请求 |
| Tier3/Tier4 后置过滤分支 | 垃圾源从根源不进入链路 | 代码 ~50 行 |
| URL 黑名单正则脚本 | 白名单天然实现 | 配置文件 + 匹配逻辑 |
| 低质源丢弃代码段 | 无此类数据流入 | 代码 ~30 行 |

### 必须保留的核心模块（不可简化）

1. **Supabase URL 去重** — 同篇新闻多源转载只入库一次
2. **AI 语义相关度打分 (0–100)** — 同一 BBC 页面也有无关内容，≥60 入库
3. **同事件多信源交叉校验** — T1 记者之间爆料可能冲突，消息可能反转，需 AI 聚类+冲突标记+T0 官方兜底
4. **事实/主观观点自动区分** — 发布会原话（事实） vs 记者预测（推论）

## 精简后架构流程

```
Supabase 白名单 (T0/T1/T2)
  → Cron 触发
  → 定向串行抓取（Firecrawl 主路径；余额不足自动降级 scraper-direct.js）
  → URL 去重
  → LLM 相关度打分 (≥60)
  → 事件聚类 + 多源交叉校验
  → Tier0 冲突检测
  → 写入 articles 表
  → 生成 Markdown 日报
  → React 前端按 Tier/时间检索
```

**变化量：** 相比旧方案，代码行数↓40%，API 调用量↓40%，运行耗时↓40%。

## 关键设计洞察：为什么白名单优于黑名单

黑名单思路（旧方案）："搜全网 → 检查每篇文章来自哪里 → 来自《太阳报》的打 T4 标记 → 丢弃"——需要维护一个低质量源黑名单，且每次运行都在浪费算力处理终将被丢弃的数据。

白名单思路（新方案）："只去 BBC、The Athletic、MEN 的页面抓"——不给垃圾源发请求，不存在"混入"的问题。这是从源头消除噪声，比事后过滤更可靠也更简单。

## 数据模型无破坏性改动

```
keywords
  └── keyword_sources (tier ∈ {0,1,2}, fetch_type='firecrawl')
        └── scrape_url → Firecrawl 请求目标
        └── source_name, tier → 文章继承

articles
  └── source_tier ← 从 keyword_sources.tier 继承
  └── UNIQUE(keyword_id, url) → 天然去重
```
