改造 ①：智能 commit message 生成

怎么做

git-commit.js --generate：自动 git diff --cached → 发给 DeepSeek 分析改动范围（改了哪个模块、什么类型）→ 生成 conventional commit 格式的 message → 输出 JSON {success, message, type, scope, changed_files}。AI 从此不用手想 commit message，也不用记 -p/-n/--amend 这些 flag。

原 node scripts/git-commit.js "feat: xxx" 手动模式完全兼容。

改造 ④：ai.js 真 function calling

怎么做

analyzeResultV2：用 OpenAI-compatible tools 参数定义 report_article_analysis function（score/summary/event/event_type/category），tool_choice: {type:"function", function:{name:"report_article_analysis"}} 强制模型按 schema 返回。不再需要 v1 的"prompt 让模型输出 JSON → text.match(/\{[\s\S]*\}/) 正则提取"。

Phase 3 · 组合化 2.0 — 上下文感知的工具编排
预计 3-5 天
子任务 A：工具链图（Tool Graph）

目标：定义工具间的依赖关系。AI 修改了前端文件 → 自动触发 type-check + lint；修改了后端文件 → 自动触发 node --check + test。

实现思路：在 registry.js 给每个工具加 triggers_on 字段 —— 声明"哪些文件变更应该触发这个检查"。AI 改完文件后，根据变更路径自动选出需要跑的检查项。inspiration 来自 Anthropic 的 Tool Search Tool 概念——不是把所有工具全加载，而是基于上下文按需发现相关工具。

具体做：

  • 给 registry.js 的工具加 triggers_on: ["src/*.js", "src/**/*.js"] 等匹配规则
  • 创建 src/tools/graph.js — 根据文件变更列表计算需要触发的检查工具
  • 在 CLAUDE.md 中更新调用规则："修改 src/ 下的 .js 后自动触发 check_all；只改 client/ 下的 .tsx 后只需 check_type"
子任务 B：response_format 枚举

目标：AI 能控制工具返回的详细程度。灵感来自 Anthropic "Writing effective tools for agents" 中建议的 response_format: concise | detailed 模式。

具体做：

  • 给每个工具的 parameters 加 response_format 可选枚举
  • concise = 只返回成功/失败 + 关键数字（给 AI 节省 token）
  • detailed = 完整输出含日志、堆栈（人类排查问题时使用）
  • 默认 AI 调用时用 concise，人类在终端调用时用 detailed
子任务 C：commit_git 参数感知

目标：AI 调用 commit_git 时，message 参数基于当前 git diff 自动预填充，不需要 AI 手想。Phase 2 的 --generate 已经做到了分析 diff → 生成 message，Phase 3 更进一步：把 --generate 的逻辑嵌入 registry.js 的 return_schema 和 description 中，让 AI 知道"这个工具会自动生成最佳 message，传 null 即可触发自动生成"。

子任务 D：跨工具状态传递

目标：上一个工具的 return 能作为下一个工具的 input。例如 pipeline_run 返回 {"relevant_items": 12} → AI 自动判断"产出充足，不需要额外操作"或"产出太少，建议 data_backfill 重跑"。

实现思路：在 registry.js 给每个工具加 suggest_next 字段——声明"本工具执行后，基于返回值建议的下一个工具"。AI 读取 return_schema 后结合 suggest_next 做出下一步决策。

Phase 4 · 自治化 — 自愈 + 评测 + 学习
预计 1-2 周
子任务 A：自愈闭环

目标：harness 检测到失败 → 返回诊断建议 → AI 根据建议尝试自动修复 → 重新运行 check → 确认通过或上报。整个流程由 AI 驱动，不需要人肉介入。

流程：

  1. AI 修改代码 → harness-check --json 检测失败
  2. harness-diagnose.js 返回结构化诊断：{issues:[{message, suggestion, file, line}]}
  3. AI 根据 suggestion 修复代码（改写错误行、补缺失的分号/括号/import）
  4. AI 调 check_all 重新验证
  5. 通过 → commit；仍失败 → 重复诊断循环（最多 3 次，然后上报用户）

具体做：参考 Anthropic 的 SWE-bench agent：模型根据测试失败反馈自我修正，循环直到通过或达到上限。本项目的 harness 体系已经提供了诊断输出（Phase 2），缺的是"AI 读诊断 → 自动修改提交"的编排脚本。

子任务 B：工具使用评测体系

目标：定量知道 AI 用工具的准确率，不复。建立 evaluation tasks（典型任务 + 期望的工具调用序列），每次改造后用评测数据驱动迭代。

具体做：

  • 选择 5-10 个典型任务（"修了 src/ai.js 的 bug"、"加了新的信源 URL"、"管线报告报告量太低需要排查"）
  • 记录 AI 实际调用的工具序列和结果
  • 评估指标：工具选择准确率、参数填充错误率、冗余调用数、工具描述搜索命中率
  • 创建 evals/tool-use.json 评测定义文件
  • 参考 Anthropic "Writing tools for agents" 的评估方法——用 agentic loop 跑评测，分析 tool call metrics
子任务 C：异常模式学习

目标：harness-pretooluse 从硬编码 footgun 列表升级为自适应规则。记录每次被拦截的操作和误报率，逐步调整拦截策略——不该拦的不拦，该拦的精确拦截。

具体做：

  • harness-pretooluse 每次触发后记录日志：触发规则、被拦截命令、是否误报
  • 创建 scripts/harness-learn.js — 读取日志统计每条规则的误报率，超过阈值自动降低规则优先级或加白名单
  • 新 footgun 出现时，从拦截日志中分析模式，半自动生成新规则供人工审核
子任务 D：Programmatic Tool Calling 模式

目标：大数据处理任务（回填重算、跨运行去重、批量爬取）不再逐轮调用 bash，而是让 AI 写一段脚本在本地执行，中间结果不出现在 AI 上下文。

灵感来源：Anthropic 的 Programmatic Tool Calling — Claude 写 Python 代码编排工具调用，中间结果不入上下文。实测 token 节省 37%。

具体做：

  • 在 registry.js 给 data_backfill 和 data_dedup 加 code_execution: true 标记
  • AI 调用这些工具时，工具内部跑脚本在子进程中执行，只把最终结果返回给 AI
  • 参考 run-pipeline.js 的 child_process.spawn 模式，复用其安全沙箱（env 隔离 + --no-docker flag）

💡 关键架构决策（给另一个 AI 看）

为什么是 5 核心 + 13 按需？

Anthropic 建议始终加载工具 ≤5 个，OpenAI 建议 <20 个。check_all, check_test, commit_git, pipeline_run, ops_check 是最高频 5 个——改了代码要验证、验证通过要提交、日常要跑管线、出问题要诊断。其余 13 个工具 AI 在需要时通过 getToolIndex() 获取索引（name + summary），匹配后 getTool(name) 拿完整定义。

为什么 ai.js 保留 v1 而不直接删掉？

DeepSeek 支持 OpenAI-compatible tools API，但如果极少数情况下返回空 tool_calls（兼容性边界），v2 会自动 fallback 到 v1 的 prompt+正则模式。零破坏迁移。等 v2 跑了几周管线无问题后，可以移掉 v1。

为什么 harness 要双通道（--json + 无 flag 文本）？

--json 输出是给 AI 读的（结构化），不加 flag 是人类在终端看的（原文本）。向后兼容，不影响现有 CI/CD 脚本。

Phase 3 为什么不现在做？

Anthropic 的核心建议："用简单的组合模式解决问题，仅在复杂度可证明能改善结果时才增加。" Phase 1-2 刚交付，需要先用一两周，积累实际使用数据——哪些工具 AI 选对了、哪些让它犹豫了、有没有工具从来不碰——然后再决定工具链图的具体规则。

Phase 4 的自愈闭环依赖什么？

依赖 Phase 3 的工具链图和 response_format：工具之间能互相感知状态了，才能基于"这个工具失败了"触发诊断 → 修复 → 复验流程。Phase 4 不能跳过 Phase 3 直接做。
