🧠 Anthropic 的 Tool Use 设计哲学（一句话版）

工具是"确定性系统"与"非确定性 Agent"之间的契约——它不是为了人类开发者设计的 API，而是为 LLM 的认知方式优化的接口。描述比 Schema 更重要，上下文是稀缺资源。

① Tool Search Tool（按需加载）

标记 defer_loading: true 的工具不消耗初始上下文，需要时由模型自行搜索发现。从 77K → 8.7K tokens（节省 95%）。Opus 4 MCP 准确率从 49% 跃升至 74%。

来源: Introducing advanced tool use, 2025-11-24

② Programmatic Tool Calling

让 Claude 通过 Python 代码编排工具调用，中间结果不出现在上下文。平均节省 37% token。消除 19+ 次重复推理往返。

来源: Introducing advanced tool use, 2025-11-24

③ Tool Use Examples

input_examples 教模型何时包含可选参数、参数如何关联。复杂参数准确率从 72% → 90%。用真实数据展示 minimal/partial/full 三种模式。

来源: Introducing advanced tool use, 2025-11-24

④ 工具描述是第一优化手段

Anthropic 在 SWE-bench 中花在优化工具定义上的时间超过了优化 prompt。每个工具至少 3-4 句描述：做什么、何时用/何时不用、边界条件。

来源: Writing effective tools for AI agents, 2025-09-11

"如果你在写正则表达式从模型输出中提取决策，那个决策应该是一个工具调用。从自由文本中解析结构化意图说明结构应该放在 schema 中。"

—— Anthropic 官方文档, How tool use works

OpenAI 核心洞察

① Strict Mode（结构化约束采样）

设置 strict: true，模型输出 100% 符合 JSON Schema。通过 grammar-constrained sampling 实现。建议几乎所有 function calling 都用 strict。

来源: platform.openai.com/docs/guides/function-calling

② Tool Search / defer_loading

GPT-5.4+ 支持。与 Anthropic 同方向：只加载高频工具，其余按需发现。配合 allowed_tools 可在不改变工具列表的情况下限制可用子集。

来源: platform.openai.com/docs/guides/function-calling

③ 命名空间（Namespaces）

用 type: "namespace" 包裹相关工具（如 crm、billing、shipping）。帮助模型在"相似但属于不同系统"的工具间做出正确选择。

来源: platform.openai.com/docs/guides/function-calling

④ tool_choice 精细控制

auto / required / none / 强制特定工具 / allowed_tools 五种模式。并行调用可关闭 (parallel_tool_calls: false)。

来源: platform.openai.com/docs/guides/function-calling

📊 差距分析

对照清单：官方最佳实践 vs 项目现状

官方最佳实践项目现状差距
结构化 Function Calling 工具定义（name + description + JSON Schema）✗ 无。AI 调用全靠 bash("npm run xxx")🔴 严重
Strict mode / 约束采样确保参数合规✗ 无。脚本靠 node 参数校验，无 schema 层🔴 严重
工具按需加载（< 10 个直接加载，> 10 个按需）△ 项目脚本 < 10 个但缺少加载机制🟡 可优化

Tool Use Examples（输入示例）✗ 无。AI 只能靠记忆猜参数格式🔴 严重
错误处理：is_error + 可操作信息让 Agent 自愈△ harness 能拦截错误，但不给 Agent 自愈建议🟡 可优化
并行工具调用（独立操作批处理）✗ 无并行机制。每次 bash 调用串行🔴 严重
命名空间分组（按领域给工具加前缀）△ ops: / check / commit 有隐式前缀但不统一🟡 可优化
工具返回值精简（只返回 AI 需要的字段）△ 脚本 stdout 混杂进度消息和结果🟡 可优化

结论：项目在"命令别名"和"简单组合"层次做得不错（harness 四件套是亮点），但在结构化工具定义、智能路由、上下文感知、代码编排这四个维度几乎是空白。

🗺️ 四阶段优化路线

1

Phase 1：结构化 —— 给每个工具穿上"AI 能理解的外衣"

⏱ 预计 1-2 天
  • 创建 tools-schema.json：把每个 npm script 和 harness 脚本写成 OpenAPI/JSON Schema 格式，含 name、description（3-4 句）、parameters、required、input_examples
  • 示例改造 —— 把 npm run check 变成结构化工具： 
    {
  "name": "project_check",
  "description": "运行项目全套验证流程，包含后端语法检查、前端类型检查、前端 Lint 和全量测试。适合在修改代码后提交前运行。不支持只跑部分检查——若只需语法检查请用 syntax_check 工具。",
  "parameters": { "type": "object", "properties": {}, "required": [] },
  "input_examples": [
    { },
    { "comment": "工具无参数，总是跑全套检查" }
  ],
  "return_schema": {
    "passed": "boolean",
    "stages": { "lint": "pass|fail", "type_check": "pass|fail", "test": "pass|fail" },
    "failures": ["string"]
  }
}
  • 为 git-commit.js 创建结构化工具定义：把 -p -n --amend --dry-run -a --all 这些 flag 变成明确的 boolean 参数
  • 建立 tools registry：一个 src/tools/registry.js，集中管理所有工具的 schema 定义
2

Phase 2：智能化 —— 让 AI 自己选择合适的工具

⏱ 预计 2-3 天
  • 引入 OpenCLI 结构：给每个脚本输出加上 JSON 模式（--json flag），让 AI 读取结构化结果而非解析混杂的 stdout
  • Harness 输出诊断化：posttooluse/stop 不再只报"通过/失败"，而是输出结构化建议： 
    // harness 输出示例
{
  "status": "fail",
  "failures": [
    { "file": "src/ai.js", "line": 142, "type": "syntax",
      "message": "Unexpected token '}'",
      "suggestion": "检查第 140-143 行的括号配对，可能多了一个 }" }
  ],
  "summary": "1 个语法错误，0 个类型错误，0 个测试失败"
}
  • run-pipeline.js 增强：输出结构化状态文件（不仅是 JSON，而是带阶段状态、错误详情、重试建议的完整诊断）
  • 建立 tool_choice 路由：在 agent system prompt 中说明何时用哪个工具（如"修改了 src/ 下 .js 文件后应调用 project_check；修改了 client/ 下 .tsx 文件后应调用 type_check"）
3

Phase 3：组合化 2.0 —— 上下文感知的工具编排

⏱ 预计 3-5 天
  • 实现工具链图（Tool Graph）：定义工具间的依赖关系——AI 修改了前端文件 → 自动触发 type-check + lint；修改了后端文件 → 自动触发 node --check + test
  • 智能 commit 消息生成：基于 git diff 内容，AI 自动分析改动范围（哪个模块、什么类型），生成 conventional commit 格式的 message，填充到 commit 工具的参数中
  • 流水线状态感知：run-pipeline.js 不再只是"成功/失败"，而是返回各阶段执行结果，让 AI 知道具体哪步失败了、为什么、建议的重试策略
  • 工具响应格式化：所有工具输出加上 response_format 枚举（concise vs detailed），让 AI 控制返回内容的详细程度
4

Phase 4：自治化 —— AI 能自愈、自优化

⏱ 预计 1-2 周
  • 自愈闭环：harness 检测到失败 → 返回诊断建议 → AI 根据建议尝试自动修复 → 重新运行 check → 确认通过或上报
  • 工具使用评测体系：建立 evaluation tasks，定量测量 AI 在典型任务中的工具调用准确率、冗余调用数、错误率。用数据驱动工具描述的迭代优化
  • 异常模式学习：harness-pretooluse 从硬编码 footgun 列表升级为自适应规则——记录每次被拦截的操作和误报，逐步调整拦截策略
  • Programmatic Tool Calling 模式：对于批量数据处理任务（如回填、去重），让 AI 写代码在本地执行而非逐轮调用 bash，大幅减少往返次数

🤝 与 Function Calling 的关系

直接回答你的问题

Function Calling 就是 Tools 元能力在 LLM 世界的"标准通路"。

你文档里讨论的"把 bash、grep 包装成强化工具"——那个"包装"的过程，在 OpenAI 叫 function calling，在 Anthropic 叫 tool use。本质完全相同：都是把原本需要 AI 手动拼命令字符串的元能力，升级为带 schema、带描述、带示例的结构化接口。

🔧 无 function calling（当前状态）

AI 每次都要用 bash("npm test -- --coverage")——需要记住完整命令、参数格式、flag 名称。一个拼写错误就全崩。这和人类在命令行里手动输入没有区别。

→ 元能力的"原材料"态

⚡ 有 function calling（优化后）

AI 调用 run_tests(coverage=true)（结构化 JSON），你的代码负责展开成 npm test -- --coverage。AI 不再需要知道底层命令行语法。

→ 元能力的"加工"态

"工具强化不是创造新能力，而是让元能力以更高效的方式被调用。Function calling 就是这种强化的标准形式——模型通过结构化 JSON 发出调用意图，而非通过自由文本拼命令。"

裸元能力（当前）Function Calling（目标）
AI 调用方式bash("npm test -- --coverage"){"name":"run_tests","arguments":{"coverage":true}}
参数校验无——AI 拼错 flag 就失败JSON Schema 在 API 层校验
错误处理stderr 混杂一大堆文本结构化 is_error + suggestion
工具选择AI 靠记忆/试错从 tool list 按 description 匹配
并行调用每行 bash 串行执行一次发多个 tool call 并行
上下文效率原始命令字符串 + 巨量 stdout精简 schema + 筛选后返回

你的 ai.js 已经在做类似的事，但方向反了

注意 src/ai.js 里 analyzeResult() 的那些 prompt 工程——你在用 prompt 引导 DeepSeek 输出结构化 JSON，然后再 parseAnalyzeResult() 用正则提取。这本质上是手动实现了一个非标准的 function calling：

  • 你把 expected output schema 写在 prompt 里（而非 tools 参数里）
  • 你用正则 text.match(/\{[\s\S]*\}/) 提取 JSON（而非原生 structured outputs）
  • 你手动做 score range 裁剪（而非 strict mode 自动保证）

如果 DeepSeek 支持 structured outputs / function calling（它确实支持 OpenAI-compatible 的函数调用接口），你完全可以把这些 prompt 里的 schema constraints 挪到 tools 参数中，让模型在生成时就受约束，省去正则解析的风险。

🚀 这些优化到底对 AI 推进项目开发有什么帮助？

🧠

降低认知负担

AI 不需要记住 npm test -- --coverage --watchAll=false --silent 这种咒语——一个 run_tests 工具封装了所有细节。Anthropic 的数据：精确的工具描述能让模型正确率跃升 25%。

⏩

加快开发循环

一次发 5 个并行 tool call（lint + type-check + test + format-check + build-check），而非 5 轮串行 bash。从分钟级变秒级。OpenAI 的默认行为就是并行调用。

🛡️

减少低级错误

Strict mode 保证参数 100% 符合 schema——不会再有"多打了个 --"或"掉了引号"这类 typo 级错误。你的 harness pretooluse 也就不用硬编码那么多 footgun 了。

💰

节省 Token 成本

工具按需加载 + PTC 代码编排可节省 37-95% token 消耗。对大项目意味着更少的 API 费用、更长的有效对话轮次。

🔄

实现自愈闭环

Harness 输出诊断建议 → AI 理解并修正 → 自动重跑验证 → 通过或上报。开发效率从"人肉调试"变成"AI 自愈"。

📈

可量化评估

有了结构化工具定义和评测集，你能用数据说话：工具调用准确率从 X% 升到 Y%，冗余调用减少 N%。不再靠"感觉变好了"来判断。
