在 Claude Code 中通过 Skills 构建验证循环

如何将你的手动检查转化为 skills，让 Claude 自行闭环反馈。
📂 Claude Code 📅 2026年7月22日 ⏱️ 阅读 5 分钟

大多数智能体编码会话遵循一个循环：你提出修改要求，Claude 收集上下文、采取行动、验证结果，如果需要，循环回去收集更多上下文。

验证（Verification） 是智能体在回应前检查自己工作的方式。Claude 已经通过观察代码库中的确定性信号（包括类型检查器、linter、测试和运行时错误）来做一部分验证。Claude 无法推断的部分，就变成了你手动检查功能时采取的步骤。

然而，这些手动步骤可以转化为验证循环。在 Claude Code 中，验证循环是一个迭代过程，Claude 在其中检查并尝试修复自己的工作。

🔄 智能体循环：1. 收集上下文 → 2. 采取行动 → 3. 验证结果

在本文中，我们将介绍最常见的验证循环类型，并展示我们在 Anthropic 内部使用的做法。然后我们会展示如何将你已经做的手动检查编码为 skills，让 Claude 自行闭环反馈，这样你就可以在它迭代时去处理别的事情了。

👋 刚接触智能体循环？从 智能体循环入门 开始。

什么是验证循环？

验证循环是一个重复循环，AI 智能体在其中检查自己的工作——运行测试、linter 或自定义检查——并在继续之前修复失败项。在 Claude Code 中，验证循环可以打包为 skills，因此每个会话都会自动应用相同的检查，而不依赖于人类去记住它们。

内置验证循环

在深入设计自定义验证循环之前，了解 Claude 对多种验证循环的内置支持会很有帮助。常见功能和方法包括：

  • /verify skill：构建、运行并观察应用中的变更。
  • 工具链（Toolchain）：Claude 旨在捕获并对你提供的任何工具（如 linter）的错误代码和警告采取行动。一个好的实践是在 CLAUDE.md 中列出你的确切构建和测试命令，这样 Claude 就不必去推断。
  • 代码审查（研究预览版）：一项托管的多智能体服务，在你启用的仓库中对 PR 运行自动审查。你可以手动修复发现的问题并推送，或者通过评论 @claude 来闭环（如果你已经设置并配置了 GitHub Actions，如下所述）。
  • GitHub Actions：定义一个调用带有验证 skill 的 Claude 的任务，你本地运行的相同检查会在每次推送或 PR 时触发。
  • Spec 验证：一个 skill，帮助根据仓库中的 markdown spec 验证每次变更，并修复违规项。
  • Claude Managed Agents 中的 Rubrics（测试版）：一项托管智能体服务，允许你使用独立的评分智能体（grader agent）根据评分标准验证结果。失败会自动循环回进行返工。

编写验证循环

当你有一个现有项目，并且发现自己每次 Claude 为你实现新功能时都要做同样的小修正，那么是时候将这些步骤转化为你自己的自定义验证循环了。第一步是写下你每次都会做的所有事情。

如果你正在启动一个新项目，需要弄清楚项目应该如何运作，也是如此。用简单的英语写下最佳实践版本，就像你会在第一天交给新队友那样。

💡 专业提示：这里的检查不一定是定性的才适合。“拒绝任何删除了列但没有回填步骤的迁移”是一条确定性的规则，没有通用的 linter 能捕获，但项目特定的 linter 可以。任何你不得不反复手动强制执行的事情，都适合被捕获为一个循环。

将其制作为一个 Skill

将重复步骤编码为验证循环最常见的方法是将其编写为 skill，而创建 skill 最快的方法是安装 skill-creator 插件，让 Claude 对你进行访谈：

# 安装 skill-creator 插件（在 Claude Code 中） /plugin install skill-creator # 然后让 Claude 帮你创建 skill /skill-creator 创建一个用于端到端验证前端变更的 skill。采访我的工作流程。

你也可以手动编写 skill，只需在项目中的 .claude/skills/ 目录下放一个 markdown 文件。最简单的验证 skill 就是几行 frontmatter 加上正文：

--- name: verify-log-hygiene description: 检查错误日志是否包含请求 ID，并且绝不包含请求体。 当 diff 涉及错误处理或日志记录时使用。 allowed-tools: [Read, Edit, Grep] --- 读取当前 diff 中的错误处理路径。 对于错误路径上的每个日志调用，确认它包含请求 ID 并且没有传递请求体、头部或任何用户提供的负载。 报告每个违规的文件:行号，然后修复它：在缺失的地方添加请求 ID， 并从日志调用中剥离负载。

完整的 schema 及其背后的理念，请参阅我们的 完整 skill 构建指南。

将检查匹配到运行位置

接下来要确定验证循环如何触发：独立（Standalone）、嵌入式（Embedded）、链式（Chained），还是绑定到 PR。

🔹 独立（Standalone）

你在产出工件后有意调用它。独立的 skill 适用于并非每次都需要应用的跨领域检查：提交前安全扫描、PR 前可访问性审计、仓库范围内的许可头验证。任何你想在许多工作流中可用，但不想在每次代码变更时都触发的东西。

⚠️ 代价是每次调用仍然是你需要记住执行的一个步骤。当你每次变更后都运行它时，就说明已经超出了独立模式。此时，该流程已经赢得了永久位置：将其嵌入或链式。

🔸 嵌入式（Embedded）

作为产生式 skill 的一部分自动触发。该检查属于一个特定的工作流，现在该工作流无需你要求就会运行它。

# 在技能 body 末尾追加一行 创建组件文件后，对其运行 eslint 并在报告完成前处理所有错误。

✅ 适用于你能编辑的 skill（你自己写的，或项目级安装的）。
❌ 不适用于内置或插件管理的 skill（会被覆盖）。

🔗 链式（Chained）

一个 skill 在结尾调用另一个 skill，多个验证交接端到端运行。

Anthropic 的 Claude Code 团队成员日常使用此模式：/code-review 查找 bug，/simplify 清理 diff，/verify 确认端到端行为，/design 根据 DESIGN.md 检查 UI 变更。

# .claude/skills/safe-refactor/SKILL.md 首先在当前 diff 上运行 /simplify。 当 /simplify 完成后，调用 /verify-no-public-api-changes。

📦 在每个 PR 上

一旦链在你自己的变更上稳定下来，同样的流程就可以在每个 PR 上运行。队友的变更也会通过你同样的关卡，无论他们是否记得调用链。

这是验证从个人基础设施转变为团队基础设施的地方。你写下来是为了每周省两分钟，现在它正在为每个人每次变更省两分钟。

📌 何时跳过某种模式：
• 跳过嵌入式（embedded）用于跨工作流的检查 → 用独立（standalone）
• 当步骤足够独立，有时你想单独运行其中一个时，跳过链式（chained）
• 在链还在变动时，暂缓设置 PR 级别的关卡

验证循环创建流程

一旦你掌握了流程，就可以准备扩展你的循环工程了。验证循环的创建过程是一致的，无论你在自动化什么或在什么环境中：

  1. 选择你本周最常做的手动跟进事项。
  2. 先试用内置的 /verify skill，看看它是否有助于你的流程。
  3. 用简单的英语写下该流程，就像你会在第一天交给新队友那样。
  4. 交给 skill-creator，或者自己把 markdown 文件放到 .claude/skills/ 目录下。
  5. 在新任务上调用它，确认检查作为输出的一部分运行，根据需要迭代。
  6. 尝试 skill 链式来创建端到端的验证流。

你为 Claude 编码得越多，Claude 的回应就越能在第一次尝试时接近你想要的。你不再需要手动调整的那些修正，现在释放了你的注意力，让你可以去处理那些没有 skill 能为你写下的、独一无二的工作。

开始使用 Claude Code 中的验证循环。
