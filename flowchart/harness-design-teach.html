一、一句话：Harness 是什么

模型是大脑，Harness 是脚手架——模型自己之外的所有东西。Anthropic 对它的定义是：

"the software scaffolding around a model: the loop, tools, context management, and guardrails." — Anthropic, Harness Design for Long-Running Application Development

四个词正好对应四个支柱。理解这件事的第一性原理是下面这句：

"Every component in a harness encodes an assumption about what the model can't do on its own, and those assumptions are worth stress testing." — 同一个 harness 的每个组件，都在编码「模型靠自己做不到什么」的假设

换句话说：你加护栏不是因为护栏本身好，而是因为模型会做 X，你不想让它做。你加进度文件，是因为模型不记得上一轮干了啥。等模型变强（比如上下文焦虑消失），有些组件就废了——但新天花板需要新脚手架。

"The space of interesting harness combinations doesn't shrink as models improve. Instead, it moves." — Harness 不会缩小，只会移动

→ 所以别指望一次性建完美 harness。先补当前模型缺的，模型进步了再拆。这一条你已经做对了。

二、四根支柱

🔄
Loop 循环
Agent 的工作节拍：Gather Context → Take Action → Verify Results。
长任务里最重要的变体是 GAN 式循环：做的人（Generator）和评的人（Evaluator）分离。
🛠️
Tools 工具
文件系统是最基础的持久化原语。
「10 个聚焦工具胜过 50 个重叠工具」，给 agent 一个 bash 常常比预建一堆工具更好。
📋
Context Mgmt 上下文
Compaction（就地总结）≠ 够用。长任务真正需要 Context Reset：清空窗口 + 靠结构化交接文件重建。Skills 的渐进式披露 = 按需加载。
🛡️
Guardrails 护栏
Hooks 生命周期拦截 + 权限门。「成功静默，失败冗长」。每个规则应可追溯到一次具体的过往失败（ratchet 模式）。

每个支柱背后的「模型做不到什么」假设

支柱组件它编码的假设（模型做不到…）
LoopGenerator/Evaluator 分离模型是糟糕的自我评估者——"agents tend to respond by confidently praising the work—even when the quality is obviously mediocre"。所以做的人和评的人要分开。
Tools文件系统、bash模型记不住、也握不住太长的状态——把状态落盘，比塞进上下文可靠。
ContextContext Reset 交接文件Compaction 不够——Agent 会因「上下文焦虑」提前收尾（"wrapping up work prematurely"），于是需要彻底重置 + 交接文件重建。
GuardrailsHooks / 权限门模型会做危险动作，或会静默失败。权限门拦危险动作；"failures are verbose" 逼它暴露失败。
✅ 先记住这个心法
任何 harness 决策，都先问一句：「这个组件是替模型补什么它自己做不了的事？」补得对，组件就有价值；模型升级后它自然该拆。

三、三代理架构：Planner → Generator ↔ Evaluator

这是那篇文章的核心。受 GAN（生成对抗网络）启发：让一个 agent 做，让另一个更挑剔的 agent 评，反馈回流。

📐 Planner
把 1-4 句话的 prompt
扩成完整产品 spec
→
🔨 Generator
按 sprint 取一个 feature
实现 → 自评 → 交 QA
⇄
🧪 Evaluator
像用户一样点运行中的应用
按硬阈值打分 → 写 critique
角色职责原文案例
Planner把一句话需求扩成完整 spec，聚焦产品上下文和高层技术设计（不是详细实现），还找机会把 AI 特性织进 spec。一句话 → "16-feature spec spread across ten sprints"
Generator按 sprint 从 spec 拿一个 feature 实现，每轮末尾先自评再交 QA。前端 harness 每轮评估后做战略决策：得分趋势好就 refine，否则 pivot。荷兰美术馆第 10 轮整个推翻重做成 CSS 3D 空间
Evaluator用 Playwright MCP 像用户一样点击、测 UI/API/DB 状态；按多个带硬阈值的维度打分，"if any one fell below it, the sprint failed"。核心引语："Out of the box, Claude is a poor QA agent."抓到真实 bug：PUT 路由顺序错误、delete-key 状态不一致

两个关键机制

① Sprint Contract — 对等谈判，不是下发
每个 sprint 前，Generator 提案「done」的定义，Evaluator 审查，两边迭代到一致（"The two iterated until they agreed"）。粒度极细：Sprint 3 一个就有 27 条验收标准。

这个「先协商再开工」的环节，本质上是在训练评估器的判断标准——它逼 Evaluator 在动手前就想清楚什么算完成。这是 GAN 架构的灵魂，不是装饰。
② Context Reset — 交接文件，不是全靠会话记忆
长任务里每个 agent 换手 = 清空上下文窗口，靠一个结构化 handoff artifact携带 "previous agent's state and the next steps" 重建。

通信全走文件："one agent would write a file, another agent would read it and respond." 注意：文章后来用 Opus 4.5 时因为上下文焦虑基本消除，把 context reset 撤掉了，改用自动 compaction——这印证了「harness 只移动不缩小」。
"Separating the agent doing the work from the agent judging it proves to be a strong lever."

五、三个系统性偏差（原文 vs 你的落地）

偏差 1：Sprint Contract 从「对等谈判」降格成了「自上而下下发」

原文你的实现
谁定「done」Generator 提案 → Evaluator 审查 → 迭代到一致Planner 写合同 → Generator 执行 → Evaluator 验收
性质对等协商，双方都有否决权自上而下，合同是既定的
影响评估器的标准被「前置协商」校准评估器只是按合同验收——对抗校准环是空的
为什么重要
你拿到了 GAN 架构的外壳（三个角色 + 文档），但丢了它最有价值的部分：评估器判断标准的校准过程。原文的 evaluator calibration 靠的是 few-shot 评分示例 + "read the evaluator's logs, find examples where its judgment diverged from mine, and update the QAs prompt"。合同不经协商，这个校准循环就无从谈起。

偏差 2：「三代理」落地是 worktree + 文档，不是独立 brain + context reset

原文你的实现
Agent 隔离独立 context window（separate brain），换手 = 清空窗口git worktree（物理文件隔离），主会话 + subagent
状态传递结构化 handoff artifact 重建上下文文档协议 + PROGRESS.md
真实情况每轮都是干净的新脑子上阵共享主会话上下文，没有真正的 context reset
为什么重要
物理隔离 ≠ 上下文隔离。三个 worktree 隔离的是文件，不是大脑。真实跑起来是「一个主会话指挥 subagent」——对单人项目这可能够用，但把它说成「对齐 Anthropic 原生架构」是过誉。证据：HANDOFF 声称 AGENTS.md §「三代理工作模式」定义了 Planner 输出规范，但 AGENTS.md 里根本没有这一节；B2 pre-commit 钩子也是休眠的（需手动配置才激活），HANDOFF 却把它列为「已有护栏」。

偏差 3（轻）：Guardrails 来源混淆

那篇文章不含 hooks / permissions / "success silent, failures verbose"
这些是 Claude Code 的 harness（settings.json hooks）概念，不是这篇文章的。你的 A1/A2/B1/B2 是真实有效的好东西——只是来源是 Claude Code，不是这篇。你的 insights HTML 其实标对了（"Hook 设计原则"来自社区），只是 HANDOFF 把它们当成了文章的推荐。

六、四个会咬人的坑（来自代码评审）

坑 1：功能 B 的抓取层是 stub → 端到端永远跑不出推送
src/fetch-breaking.js 第 59 行硬编码 return []，注释写着 "Phase 2"。于是 scripts/breaking-check.js 永远拿不到候选，后面的过滤/推送逻辑全都不执行。28 个测试全绿，但测的是永远不会被调用的纯逻辑。
坑 2：notify.sendBreakingAlert 不存在 → 静默降级，恰好违背「失败要响」
scripts/breaking-check.js:92 调用 notify.sendBreakingAlert(...)，但 src/notify.js 的导出是 notify(payload, opts)，根本没有 sendBreakingAlert 方法。调用必抛 TypeError → 落入 catch → 写进文件日志。

这正好违反你们自己的原则 "failures are verbose"——失败应该响，它却静默了。你管这个叫「优雅降级」，但它掩盖了「集成从未发生」。
坑 3：diagnose.js 头部声称「LLM 兜底」，代码没实现
src/diagnose.js 注释写着 "falls back to LLM diagnosis for unknown failures"，但代码里当没有模式匹配时直接返回 rootCause: 'UNKNOWN' + confidence 0.3，根本没有 DeepSeek 调用。声称的能力 ≠ 已实现的能力。
坑 4：Windows shell 不一致 + 危险路径零测试
  • diagnose.js:44 用 /dev/null、repair.js:63 用 nul，在 Windows shell:true 下前者无效 → crawl4ai 健康探测可能静默失败。
  • 测试只覆盖了 fallbackSource（一个 no-op）。restartDockerEngine / restartCrawl4ai 等高风险操作完全没测——而这恰恰是「自动重启容器」这种高风险动作，最该有测试。

    总体结论
    方向对、骨架真、机制有出入。你读对了文章、四支柱理解到位、确定性检查优先的判断完全正确——这些比大多数人都强。现在需要做的是：把「对等谈判」补回来、让文档和实际机制一致、把功能 B 的 stub 和静默失败处理掉。做完这四件事，你的三代理架构就真的「对齐」了。
